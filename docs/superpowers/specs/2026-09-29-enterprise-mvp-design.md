# Enterprise MVP design

Source requirements: `xiaochuan886/ZCode` issues #1–#9. This design records the implementation choices for the approved two-layer architecture. It was revised twice for the Customer workspace model: first removing the ServiceSpace/ServiceObject/Case hierarchy entirely, then — the current revision — moving the runtime owner from the Customer to the **expert** (the service provider's operator). The product's primary loop is one expert maintaining many Customers; the expert's environment is the long-lived entity, and Customers are workspaces inside it.

## Product model

- The tenant is a technical service provider. Its users are **experts** (and tenant admins). One expert maintains many Customers concurrently; multi-user collaboration exists but is secondary.
- The **expert runtime** is the long-lived unit: one runtime per (user, tenant), with the expert's own HOME data volume (their global Skills, MCP, settings, task index, memory).
- A **Customer is a workspace** inside the expert runtime. All of the tenant's Customer workspace directories are mounted into each expert runtime of that tenant; the native server advertises them all (`ZCODE_SERVER_WORKSPACES`). Switching Customers is a native workspace-tab switch — no runtime handoff, no Root teardown, no gateway round-trip.
- Isolation decisions (approved): sessions are isolated per expert (each expert has a private runtime, HOME and task index); inside a tenant, Customers are trusted to the tenant's own experts ("same tenant = trusted"); multiple experts concurrently working the same Customer workspace are accepted for the MVP (documented risk: concurrent agent writes to the same files). Between tenants, isolation stays hard — separate runtimes, volumes and credentials.
- Customer CRUD (create/update/delete) is **admin-only** and lives in the settings surface, not a landing page.

## Boundary and ownership

- A new `@zcode/enterprise` package owns users, tenants, memberships, Customers, Customer Skills, MCP bindings and their relay tokens, tenant shared Skills, the tenant model credential, and the session's last-opened Customer. Its SQLite database is the sole owner of these facts.
- Existing ZCode owns Composer, sessions, modes, tools, files, Skills execution, MCP execution, plugins and permission decisions. Enterprise code neither copies the conversation nor changes Agent runtime types.
- The enterprise HTTP gateway is the browser's sole origin. It authenticates every enterprise API and native runtime HTTP/WebSocket request, resolves the session's user and tenant, and forwards to **that expert's runtime**. It denies trusted-host, remote-connect, callback and other privileged runtime endpoints from normal browsers.
- Each Customer has one immutable, distinct absolute workspace directory. The native v4 session `workspaceId` is this path. Native sessions ("cases" in product language) live inside a Customer workspace and are owned by the expert whose runtime created them.

## Identity and data

`EnterpriseStore` is the sole writer of enterprise rows. Every tenant-owned read or write starts with an actor user ID, checks current membership, then checks the parent chain in one SQLite transaction. Cross-tenant and absent resources return the same `not_found` error. Customer workspace paths are generated from the server-controlled root and opaque Customer ID. Session rows store only a SHA-256 digest of the browser bearer token, a CSRF token digest and the last-opened Customer ID; membership is checked again on each resolve. Revoking a membership invalidates that member's active access immediately. Schema upgrades use `PRAGMA user_version` within a transaction, and foreign keys are enabled on every connection.

The authentication sequence is `password verification → issue random session and CSRF secrets → set HttpOnly SameSite cookie → resolve digest on each request → check current membership → validate Origin and CSRF on mutation`. Passwords use scrypt with a per-user random salt and constant-time comparison. The operator bootstrap command takes its password from a TTY prompt or stdin without printing it.

Membership roles are `admin` and `member`. An admin manages tenant members, the tenant model credential, tenant shared Skills, and Customer CRUD. Members open and work in their tenant's Customers but never mutate the customer catalog, shared Skills, MCP bindings or credentials.

## Runtime and routing

```text
browser request /ws or /api/*
  → gateway authenticates the session user and tenant
  → runtime manager ensures the EXPERT runtime exists (id = user+tenant)
  → gateway forwards to that runtime with its private token
  → native ZCode HTTP/RPC service executes (all tenant Customer workspaces hosted)
```

The expert runtime id is derived from (user id, tenant id); a user active in two tenants gets two runtimes. The runtime's HOME is the expert's own data volume under the gateway data root; every tenant Customer workspace is mounted read-write; the container starts with `ZCODE_SERVER_WORKSPACE` set to the last-opened (or first) Customer workspace and `ZCODE_SERVER_WORKSPACES` advertising all of them. The native proxy and websocket routing never depend on which Customer is active: one session maps to one expert runtime for its whole lifetime.

Customer activation is bookkeeping only: it records the last-opened Customer for the next bootstrap and needs no socket close, Root teardown or runtime restart. The gateway resolves routing from the session's user, not from the active Customer. Membership removal closes that user's sockets and stops their runtimes; cross-tenant access keeps returning 404.

**Idle reaping and concurrency cap** (both opt-in via environment, default off): `ZCODE_ENTERPRISE_RUNTIME_IDLE_MINUTES` stops an expert runtime that has had **no attached session sockets and no MCP relay activity** for the whole window — the reaper stops runtimes through the same fail-fast path used by mutations (sockets destroyed first), so an expert whose browser is still open simply self-heals and restarts on demand. `ZCODE_ENTERPRISE_MAX_RUNTIMES` caps concurrently running runtimes: when ensuring a new runtime would exceed the cap, the least-recently-active runtime is evicted first; under sustained overload this can thrash (each eviction disconnects one expert who then reconnects), which is accepted and visible rather than hidden. Both settings exist for capacity-bounded hosts (a 4-core/8-GB ECS keeps roughly 3 warm expert containers); disabled by default so development behavior is unchanged.

Production isolation uses one unprivileged container per expert runtime with the expert data volume and the tenant's Customer workspace volumes mounted; no host home, Docker socket or other tenant volume is mounted. Tenant boundary = runtime boundary = credential boundary. The process adapter is development-only. Runtime listeners bind loopback or a private container network and use a random per-runtime token. The gateway never returns direct runtime addresses or tokens to browsers. Native `/api/rpc-host-capability`, `/ws/host`, remote-connect and bot callback routes are denied at the gateway; the native proxy canonicalizes paths, strips hop-by-hop headers and replaces browser credentials with the runtime token as before.

Runtime lifecycle: starts are idempotent per expert runtime id; a health check reattaches or replaces an unhealthy or stale container; gateway shutdown stops all live runtimes. Expert runtime preparation distributes (a) the tenant model credential into the expert's `.zcode/v2/provider_config.json` managed slot and (b) tenant shared Skills into the expert HOME `.zcode/skills/enterprise-*`. Customer workspaces are materialized at Customer CRUD time (below), not at runtime start.

## Model provider distribution

The tenant admin maintains a **provider catalog** (schema v7 `tenant_model_providers`): any number of providers per tenant, each with a stable `provider_key` slug (unique per tenant), display name, API type (`anthropic-messages` or `openai-chat-completions`), HTTPS public base URL, API key (AES-256-GCM at rest, tenant-bound AAD — same envelope as before), a list of model IDs, a default model, an enabled flag and a tenant-wide default marking. Exactly one enabled provider is the tenant default (creating the first provider marks it default; switching the default clears the siblings). `EnterpriseStore` remains the sole owner of the keys; rotation and revocation are row updates. Migration v7 seeds one provider row from the legacy single credential when a tenant has one and no catalog rows yet; the legacy single-credential HTTP routes are removed in the same change.

When an **expert runtime** is prepared, the control plane distributes every enabled provider into that expert's native provider configuration (`.zcode/v2/provider_config.json` inside the expert data volume): each provider becomes a managed `enterprise-<provider_key>` slot carrying the real upstream base URL, the real API key and its model list; the tenant-default provider pins the default model selection. Members never configure providers: the native settings surface hides the model provider section, and the runtime server (started with `ZCODE_ENTERPRISE_MANAGED_MODEL=1`) rejects provider configuration writes, Z.ai OAuth mutations and generic credential RPCs (`enterprise.model_configuration_managed`); provider status/model reads stay available — switching the active model among the distributed slots is native behavior and stays allowed. Model traffic flows directly from the expert runtime to the upstream provider — no relay on the request path.

An admin-only connection-test route performs a best-effort model list against the provider (Anthropic `x-api-key` or OpenAI `Authorization: Bearer` depending on API type, short timeout) and returns `{ok, models?, error?}`; the API key is never logged.

Distribution invariants: keys are written only into expert data volumes of that tenant; the provision step rewrites all managed slots atomically on every runtime start; previously managed slots are replaced rather than accumulated (deleted catalog rows disappear from the slot set); unmanaged entries are preserved. The API key never appears in gateway logs, API responses or browser state; only status projections (enabled/default, last four) leave the store. Catalog changes stop the tenant's expert runtimes so the next open re-distributes.

## Customer workspace, Skills and MCP

Materialization happens at **Customer CRUD time** (admin action), deterministically, and is independent of any runtime: creating or updating a Customer writes a minimal `AGENTS.md`, the Customer's Skills under `.zcode/skills/enterprise-*`, and MCP relay entries into that workspace's `.zcode/config.json`. Customer CRUD stops the tenant's expert runtimes first: container mounts are fixed at start, so a new or renamed Customer requires a runtime restart to be visible; stopping at CRUD time also guarantees no running runtime holds stale workspace files. User edits to generated files are overwritten by the next materialization; this is stated in the UI.

Skills are layered by owner. **Tenant shared Skills** (admin-managed, `tenant_skills`) are distributed into every expert runtime's HOME — one copy per expert, refreshed at runtime preparation. **Customer Skills** (source Customer recorded, content hashed) live only in that Customer's workspace and are materialized at CRUD time. **Expert personal Skills** are whatever the expert keeps in their own HOME — native behavior, untouched. Native global-versus-project Skill separation stays intact inside each expert runtime. Admins can **promote a Skill into the tenant layer**: an admin-only listing route scans the acting admin's expert HOME and every Customer workspace of the tenant (`.zcode/skills` and `.agents/skills` — the four native discovery roots) and returns importable Skills with name, frontmatter description, origin (personal vs workspace) and an already-imported marker; managed `enterprise-*` directories are excluded. The import route (`POST /tenants/:id/skills/import`) takes name + origin (+ workspace) rather than a blind name, because skills created by the native skill-creator default to the **project level** — the active Customer workspace — so importing only from HOME would miss them. The settings UI renders the list as a picker with descriptions; the composer's own skill selector is coupled to the native runtime skill catalog and cannot serve gateway-side data, so the picker mirrors its pattern instead. Import copies the `SKILL.md` content into `tenant_skills` and stops tenant expert runtimes for redistribution; the native Skill card "share to tenant" entry is a later round.

**Native share entry and managed-content protection (Round C)**: the native skill management card gains an enterprise-only "share to tenant" action — additive in `packages/ui`, rendered only when `enterpriseContext` is present. The action passes the skill's name and source path to the shell-provided `onShareSkillToTenant` handler; the shell resolves the origin (Customer workspace matched by path prefix, else expert HOME), posts to the existing import route, warns that runtimes restart, and relies on the socket self-heal to remount. Managed names become tamper-evident at the source: with `ZCODE_ENTERPRISE_MANAGED_CONTENT=1` (set by every enterprise runtime adapter alongside the managed-model flag) the native skill-management and MCP config write paths reject create/update/delete operations whose target name uses the reserved `enterprise-` prefix (`enterprise.managed_content`), so tampering fails immediately instead of self-healing only at the next preparation. Native packages stay additive: the flag defaults to off and ordinary ZCode behavior is unchanged.

**Baseline Skill seeding**: expert runtime preparation seeds the bundled baseline Skill set into the expert HOME `~/.agents/skills/` — the standard cross-tool location with lower discovery priority than `.zcode/skills`, so an expert can still override a baseline skill with a same-name copy. The baseline set is vendored under `packages/enterprise/runtime-seed/skills/` from the official plugins: `skill-creator`, the `zcode-guide` diagnostics/configuration skills, and the document skills (`docx`, `pdf`, `pptx`, `xlsx`). Seeding is **if-missing only**: an existing directory is never overwritten (personal/native territory stays untouched), so a baseline content upgrade requires deleting the seeded directory. Seeded skills are ordinary personal-layer skills, outside the managed-names manifest. **Seed upgrades**: each seeded directory carries a `.enterprise-seed.json` marker (bundled version plus a content digest recorded at seed time); when the bundled version advances, preparation replaces seeded directories whose current content still matches the recorded digest, while directories that have diverged (expert modifications) are left untouched — upgrades refresh clean copies and never clobber personal edits. Without seeding the container has no plugin-provided skills at all — managed mode rejects Z.ai OAuth, so experts cannot install plugins inside the runtime. Built-in agent slash commands (`/goal`, `/plan`, …) do not depend on plugins.

**Baseline plugin seeding** (verified design — plugin loading is offline-safe): the container agent never obtains plugin content by itself (the image ships almost no plugin assets and writes an empty cache), but a pre-seeded plugin directory works fully offline at session start: agent startup, skill scans and command scans read only local disk, and every network path (store refresh, install) sits behind explicit UI actions with timeouts and cached-manifest fallback — no hang, no retry storm. The gateway therefore seeds a **curated plugin set from an operator-owned host directory** `ZCODE_ENTERPRISE_PLUGIN_SEED_ROOT` (layout `<name>/<version>/`, mirroring what a working desktop has under `~/.zcode/cli/plugins/cache/zcode-plugins-official/`): at expert runtime preparation each plugin is copied if-missing into the expert HOME `~/.zcode/cli/plugins/cache/zcode-plugins-official/<name>/<version>/` with the same `.enterprise-seed.json` digest-marker refresh semantics as skills (pristine copies upgrade, diverged copies are never touched), and `~/.zcode/cli/config.json` is **merged** (never rewritten) to set `plugins.enabledPlugins["<name>@zcode-plugins-official"] = true` for each seeded plugin, and `~/.zcode/cli/plugins/installed_plugins.json` is merged the same way (upsert-by-id install records with empty `installPath`, which discovery resolves to the seeded cache directory) — the install registry is the whitelist-free discovery path, because the agent rewrites the bundled-marketplace cachePath whitelist on every startup from the image's own assets and thereby hides plain cache copies. Recommended curation: plugins whose value is commands or plugin MCP and that the bundled skill seeding does not already cover (`superpowers` is the canonical pick); duplicating `zcode-guide`, `skill-creator` or the document skills makes every skill appear twice in the catalog, GUI/hardware plugins are useless in a server container, and `zcode_official`-auth plugin MCP fails by design under managed mode. Seeding never removes plugins (dropping one from the seed root leaves existing copies; removal is a HOME-level operation), and an expert disabling a seeded plugin is re-enabled by design on the next runtime restart — the baseline is managed. No marketplace metadata is seeded: loading needs cache content, the enabled entry and the install registry; the store UI remains unusable-but-harmless offline (refresh failures degrade to diagnostics).

MCP bindings are per-Customer with a per-tenant endpoint and a server-side secret reference. A secret reference must use `ZCODE_ENTERPRISE_MCP_SECRET_<TENANT_UUID_WITHOUT_HYPHENS_UPPERCASE>_<NAME>`; creation, materialization and relay each verify the tenant prefix. Each binding carries a **stable random relay token stored in SQLite** (schema v6) so every expert runtime's copy of the workspace config validates against the same token across gateway restarts. `.zcode/config.json` contains only the gateway MCP relay URL and that token; the upstream bearer secret stays in the gateway environment and is injected only when proxying. Each relay request checks the presented token against the stored binding, confirms the binding still belongs to that Customer and tenant, and streams to the configured HTTPS endpoint. Upstream destinations are denied by default and must match the tenant entry in operator-owned `ZCODE_ENTERPRISE_MCP_ALLOWLIST_JSON`; IP literals, localhost, userinfo, fragments, redirects and non-public DNS answers are rejected; every request pins a freshly resolved public IP. Relay concurrency is capped; an established SSE body may remain open with downstream backpressure. Deleting a Customer or binding removes its token. A missing secret reference emits an operator diagnostic and skips that binding.

**Tenant connectors (系统连接器)** are the MCP analogue of the provider catalog: admin-managed rows (`tenant_mcp_connectors`, schema v7) with a stable `connector_key` (unique per tenant), display name, HTTPS endpoint, outbound header name, a secret reference following the same `ZCODE_ENTERPRISE_MCP_SECRET_<TENANT_UUID_WITHOUT_HYPHENS_UPPERCASE>_<NAME>` pattern, a stable random relay token stored in SQLite (same v6 discipline as Customer bindings) and an enabled flag. At expert runtime preparation the enabled connectors are written into the expert HOME `.zcode/config.json` `mcp.servers` as `enterprise-<connector_key>` entries pointing at `/api/enterprise/mcp-relay/t/<connectorId>` with that token — through the same managed-names merge the Customer workspaces use, so the expert's personal (unmanaged) MCP entries survive untouched. The relay validates the presented token timing-safely against the stored connector and applies the identical allowlist, DNS pinning, redirect rejection and concurrency caps as Customer bindings; the upstream secret stays in the gateway environment and is injected only when proxying. Connector mutations stop the tenant's expert runtimes; managed entries self-heal on the next preparation (native-side edits to managed names are simply overwritten — per-name write rejection in the native UI is deferred). Members see connector names and status only; tokens and secrets never reach the browser. Three connector layers: **system connectors** (tenant-configured, gateway identity), **user-authorized connectors** (per-user OAuth tokens held by the relay; see below) and **personal connectors** (the expert's own HOME MCP entries, native behavior).

**User-authorized connectors (Round B)**: a connector registered with `auth_mode: "user-oauth"` carries the standard OAuth2 client config (authorize/token URLs, client id, client secret encrypted with the provider envelope, optional scopes) instead of a shared gateway secret; `secret_env` is rejected in this mode and the OAuth fields are rejected in shared mode. Each expert connects their own account: the connector list marks these connectors as requiring authorization (with the acting user's connected state), `GET /tenants/:tenantId/mcp-connectors/:connectorId/authorize` returns the provider authorize URL with a short-lived HMAC state binding the session and connector (redirect back to the same-origin gateway callback), and the callback exchanges the code server-side and upserts `user_mcp_connector_authorizations` (schema v8: encrypted access/refresh tokens, expiry, and a stable per-user relay token). Members revoke their own authorization with a DELETE; revoking stops the tenant's runtimes. Distribution: at expert runtime preparation a user-oauth connector is written into that expert's HOME only when the acting user holds an authorization — the relay entry carries the per-(connector, user) token, and the relay resolves it timing-safely to inject that user's access token, refreshing on demand via the refresh token when expired (a failed refresh yields a 503 diagnostic until re-authorization; refreshes are serialized per authorization). Allowlist, DNS pinning and concurrency caps are identical to shared connectors. Client secrets and user tokens never appear in logs, API responses or browser state.

## Web experience

There is no Customer home page. After login the shell opens straight into the native workspace: the last-opened Customer workspace (or the first Customer of the selected tenant) becomes `initialWorkspaceAbsPath` of the native `Root`, and the Root stays mounted for the whole session — Customer switching happens inside the native UI.

The native workspace ("项目") sidebar lists Customers: the active workspace reuses the native workspace row with its nested task list, and other Customers are rows that open that workspace as a native tab in the same runtime (an additive, enterprise-only bridge in `@zcode/ui`; no native entity or store changes). New tasks are created from the workspace as in native ZCode. The native sidebar's standalone "任务" (conversation-workspace) section stays hidden in enterprise mode: the conversation entry would create an app-managed workspace outside the Customer workspaces.

Customer management, tenant shared Skills, the provider catalog and tenant connectors live in an **enterprise settings surface** (a shell-level page, not the native per-workspace settings) that is **admin-only in its entirety**. Members never see an entry that opens it — the sidebar footer's enterprise menu items, the model-setup screen's button and the empty-customer screen's button are admin-gated (the model-setup screen shows a contact-admin hint instead), and a tenant switch that lands the user in a non-admin role closes an open settings page. Every settings-surface API rejects non-admins with 403, **including read routes**: the provider list, the connector list, the tenant shared-Skill list, and the per-Customer Skill and MCP-binding lists (importable-skills was already admin). Store-level listing methods stay member-callable because runtime materialization (gateway-prepare) uses them for every expert. The workspace shell keeps exactly one member-readable readiness signal: `GET /tenants/:tenantId/model-status` returns `{ready}` — true when the tenant has any enabled provider — with no catalog detail; the shell's model gate uses it instead of the provider list. User-oauth authorize/revoke stay per-user account actions at the API level (they touch only the acting user's own authorization row); their only UI entry lives inside the admin surface today, so a member-side authorization entry is deferred.

**Native presentational reuse in the settings tabs**: the settings tabs edit gateway-owned catalog data, so the native settings *containers* (`ModelProviderSection`, `SkillsSection` etc., which bind to runtime-RPC hooks like `useModelProviders`/`useServices` and edit the expert's own HOME files) cannot serve them — but the native *presentational layer* is reused wherever it is prop-driven and service-free, exported additively from `@zcode/ui` (`ProviderTemplatePicker`, `ApiKeyInput`, `McpServerForm`, `SettingsFormActions`, `SettingsFormTextarea`, `SettingsSegmentedTabs`, `Input`, plus the `ProviderSettingsTemplateView` type re-export). Ground rules: enterprise tab components never import native service hooks (`useServices`, `useZCodeStore`, `useModelProviders`) — all data stays gateway-catalog API in/out; native components bring their own i18n (the web app mounts `ZCodeIntlProvider` globally), and any new enterprise-owned strings live in per-tab string modules, not the shared presentation dictionary. Provider templates: the native builtin catalog (`zcode-builtin.json`) is runtime disk data the browser cannot read statically, so the enterprise model tab keeps its own curated api-key template list (`model-provider-templates.ts`, maintained in step with the official catalog); the picker only consumes `templateId` + `templateNameMap`, and prefill (apiType/baseUrl/models) resolves from the curated list. The MCP tab reuses the native form layer where tenant-connector semantics align (URL/headers), and mirrors the native form's field/validation patterns where they diverge (secret-env reference, oauth client fields); the Skill tab mirrors the native skill-card visuals (the native `SkillsSection` is workspace-coupled and not reusable directly).

**Model tab editor (round 2)**: the admin model tab presents the native editor experience — `ModelProviderSectionNavigation` (left nav, prop-driven) + `InlineEditableProviderCard` (the full right-side detail editor: inline rename, protocol select, base URL, ApiKeyInput, per-model rows with metadata badges, per-model enable toggle, add/delete/reorder, all injected callbacks, zero service hooks) — fed by an adapter that maps gateway catalog rows ↔ `ProviderSettingsFormProvider` and routes every card callback to a catalog PATCH (`onSave` → display name/base URL/api type/key, `onAddPersonalModel`/`onSavePersonalModelDraft`/`onSetPersonalModelEnabled`/`onDeletePersonalModel`/`onReorderModelIds` → the provider's model list). Creation keeps the template picker → prefilled draft. **Base URL and API protocol stay decoupled exactly as in native**: switching the protocol never rewrites the base URL (the select carries its path hint instead), because providers host different paths per protocol. Per-model metadata: the catalog stores rich model entries (schema v10: `{id, enabled?, contextWindow?, inputFormat?, outputFormat?, supportsToolCall?, supportsJsonSchemaOutput?}`; input accepts plain ids for backward compatibility), which feed the native row badges; template prefills bake metadata resolved offline from the official `modelConfigRules` (default `.*` rule + provider-site overrides matched by model id, api type and base URL) — the browser cannot read the runtime builtin catalog, and the expert runtime keeps resolving its own metadata from its builtin rules, so distribution stays id-only except that `enabled === false` models are excluded from the expert slot. `apiType` adds **`openai-responses`** as a third protocol (connection test lists models OpenAI-style with a Bearer key).

The Web entry probes `/api/enterprise/bootstrap` before opening a native socket. A `404` means ordinary ZCode Web mode; any other probe failure is visible and retryable. The gateway owns login, membership, the last-opened Customer, CSRF and all business records; the shell owns only UI selection and the browser socket. Login and every mutation send the CSRF token and same-origin cookies. Enterprise mode cannot open arbitrary workspaces — only the tenant's Customer workspaces are reachable, via the enterprise bridge. The shell uses Chinese/English labels based on browser language, semantic tokens, and stays usable on narrow viewports.

**Connection lifecycle**: the shell opens one native socket per (user, tenant) and must self-heal. Tenant-level mutations stop the tenant's expert runtimes to force redistribution; when the gateway stops a runtime it **destroys the sockets of every session whose active target points at that runtime** (fail-fast) instead of leaving them half-open — a half-open socket never answers another RPC, which is exactly the "skills stuck on 搜索中, commands empty" failure. On unexpected socket close the shell bumps its connection generation, unmounts the native Root and reconnects (the reconnect naturally re-prepares and restarts the runtime); intentional disconnects (tenant switch, logout) advance the generation first so the stale socket's close event is ignored. As the final defense against any other half-dead transport, the native RPC client applies a **default per-request timeout** (60 s, configurable via `requestTimeoutMs` at connect, `0` disables) that rejects with a typed timeout error instead of a promise that never settles — a broken transport surfaces as an error state rather than an infinite spinner. Logged-out visitors get the enterprise login screen (the shell renders it whenever bootstrap returns no user) — the shell never shows an indeterminate loader for an unauthenticated visitor.

All native sessions are created, listed and resumed by the native UI; the gateway stores no native session IDs. Session and task continuity come from each expert runtime's own state, so reloading restores the expert's workspaces without enterprise-side session data.

## Upgrade compatibility strategy

The enterprise layer must stay cheap to merge with `main`. Rules:

- Native packages (`ui`, `server`, `services`, `shared`, `client`, `web` outside `src/enterprise`) receive **additive-only** changes: new optional props (`enterpriseContext`, `enterpriseManagedModel`, the workspace-open bridge), new optional env (`ZCODE_SERVER_WORKSPACES`, `ZCODE_ENTERPRISE_MANAGED_MODEL`), and new conditionals behind those switches. No native entity, store, protocol or persistence shape is forked or renamed for enterprise.
- Enterprise business logic lives in `packages/enterprise` (own package, no native imports beyond the server entry contract) and `packages/web/src/enterprise/` (own directory). The audit baseline for this revision (measured `git diff main...HEAD` over `ui`, `services`, `server`, `shared`, `client` and `web/src` outside `src/enterprise`): ~1375 insertions across 42 native files, all additive (the one deliberate default change is the RPC client's 60 s per-request timeout, spec'd above).
- Upgrading = merge `main` into the enterprise branch; conflicts should concentrate in the additive seams (prop lists, env resolution, the enterprise gate points). Architecture checks and the untouched native test suites are the regression bar.
- Any change that would fork native behavior permanently (default flips, entity changes, protocol forks) is rejected at review; the mapping/projection pattern (enterprise rows ↔ native paths) is the required form.

## Acceptance and regression

Tests cover: two tenants; multiple experts per tenant; expert runtime identity (same expert across Customers shares one runtime; two experts get two runtimes; a user in two tenants gets two runtimes); cross-tenant API and runtime denial; membership revocation closing sockets and stopping the member's runtimes; Customer CRUD admin-only, materializing AGENTS.md/Skills/MCP into the workspace with stable relay tokens, and stopping tenant runtimes; model provider distribution into the expert data root (the provider catalog: multiple providers with multiple models each, per-key managed slots `enterprise-<provider_key>`, default pinning, admin-only CRUD plus connection test, legacy-credential seeding, no key leakage; the settings read routes — provider/connector/Skill/binding lists — reject members with 403, while the member-readable `model-status` readiness endpoint returns only `{ready}`); tenant connector distribution into expert HOME (managed names merge, personal entries preserved, relay token validation, admin-only CRUD); user-authorized connectors (OAuth authorize/callback/revoke flow against a fake provider, per-user token injection at the relay, on-demand refresh, distribution gated on the acting user's authorization); the native skill card share entry and managed-content write rejection; personal-Skill import from the admin's expert data volume; user management (admin-only CRUD with last-admin and self guards, join-by-email semantics, disable revoking sessions) and Customer visibility (allowlist grants: filtered lists/activation/bootstrap/importables, mount-level isolation, targeted runtime stops on changes); tenant shared Skill distribution into expert HOME; customer Skill scoping; MCP relay token validation against SQLite with allowlist/DNS pinning/backpressure; container mounts (expert HOME + all tenant Customer workspaces, nothing else); the sidebar customer rows opening native workspace tabs; native Agent smoke tests (sessions, Composer modes, files, shell, Skills, MCP, streaming). Container mode requires a relay origin reachable from expert containers. The MVP is complete only when the full suite passes in a documented container-enabled environment.

## Migration and non-goals

Enterprise mode is opt-in and leaves the ordinary ZCode server/Desktop paths intact. SQLite migrations are versioned and transactional: schema v4 dropped the legacy per-Case architecture destructively (initial development stage, no data compatibility); v5 adds `tenant_skills` (kept); v6 adds the stable MCP relay token column; v7 adds `tenant_model_providers` and `tenant_mcp_connectors` (with legacy single-credential seeding); v8 adds the connector OAuth columns and `user_mcp_connector_authorizations`; v9 adds the `users.status` column and `customer_access_grants`; v10 enriches `tenant_model_providers.models` from plain id arrays to metadata-bearing entries (`[{id, enabled?, contextWindow?, …}]`, legacy rows migrated in place). No SSO, billing, workflow engine, new RAG stack, new Agent/Session runtime, or Composer rewrite. Idle runtime reaping and the concurrent-runtime cap are implemented but opt-in via `ZCODE_ENTERPRISE_RUNTIME_IDLE_MINUTES` / `ZCODE_ENTERPRISE_MAX_RUNTIMES` (both default off). Tenant self-hosted plugin management (admin-uploaded plugin packages distributed like connectors) is future work; baseline plugin seeding covers the curated official set.

## User management and Customer visibility

Tenant admins manage members from the enterprise settings **用户 tab** (users are global identities; management is tenant-scoped membership administration). CRUD: list members (email, display name, role, status, Customer-access summary); create by email — a brand-new email creates a global user with an initial password plus the membership, while an email that already exists globally is simply **joined** into the tenant (no password needed, the existing identity keeps its credentials); edit display name, role and password (admin reset); disable (login rejected with invalid credentials, all sessions revoked, sockets closed, runtimes stopped) and re-enable; remove from the tenant (sessions revoked, runtimes stopped; the global user row survives because it may belong to other tenants). Guards: the **last admin** of a tenant cannot be removed or demoted (409), and an admin cannot remove, demote or disable **themselves** — both prevent accidental lock-out. The old bare `POST /users` / member-delete routes are replaced by the tenant-scoped routes below.

**Customer visibility** (schema v9 `customer_access_grants`, allowlist semantics): a member with **no grants sees all** of the tenant's Customers (the previous trust-all default, backward compatible); once any grant exists, the member sees exactly the granted Customers. Admins are never restricted (they manage the Customers). Enforcement is total, not cosmetic: the Customer list API filters per member; activating a non-visible Customer returns 404; the bootstrap's last-opened Customer resolves to null when no longer visible (the shell auto-activates the first visible one); the importable-skills scan only walks visible workspaces; and — the security boundary — **expert runtime mounts are filtered**: `expertTargetWithWorkspaces` mounts only visible Customer workspaces for that member, so an unauthorized workspace never exists inside the container at all. Visibility or role/status changes stop the **affected user's** runtimes (mount sets are fixed at container start) and destroy their sockets so browsers self-heal; other experts are untouched. Grant changes validate that selected Customers belong to the tenant and that "selected" mode is non-empty; switching back to "all" clears the grants.
