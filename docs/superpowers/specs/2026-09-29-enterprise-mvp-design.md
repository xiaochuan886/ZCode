# Enterprise MVP design

Source requirements: `xiaochuan886/ZCode` issues #1–#9. This design records the implementation choices for the approved two-layer architecture. It was revised for the Customer workspace model: the old ServiceSpace/ServiceObject/Case hierarchy and its compatibility layer are removed entirely (initial development stage, no data compatibility guarantee).

## Boundary and ownership

- A new `@zcode/enterprise` package owns users, tenants, memberships, Customers, Customer Skills, MCP bindings, tenant model credentials, and Customer/runtime mappings. Its SQLite database is the sole owner of these facts.
- Existing ZCode owns Composer, sessions, modes, tools, files, Skills execution, MCP execution, plugins and permission decisions. Enterprise code neither copies the conversation nor changes Agent runtime types.
- The enterprise HTTP gateway is the browser's sole origin. It authenticates every enterprise API and native runtime HTTP/WebSocket request, resolves the user's active Customer on the server, and forwards only to that Customer's runtime. It denies trusted-host, remote-connect, callback and other privileged runtime endpoints from normal browsers.
- Each Customer has one immutable, distinct absolute workspace directory and one long-lived runtime. The native v4 session `workspaceId` is this path. All native sessions ("cases" in product language) live inside the same workspace and share its files, Skills, MCP bindings and distributed model provider.

## Identity and data

`EnterpriseStore` is the sole writer of enterprise rows. Every tenant-owned read or write starts with an actor user ID, checks current membership, then checks the parent chain in one SQLite transaction. Cross-tenant and absent resources return the same `not_found` error. Customer workspace paths are generated from the server-controlled root and opaque Customer ID. Session rows store only a SHA-256 digest of the browser bearer token, a CSRF token digest and the active Customer ID; membership is checked again on each resolve and Customer activation. Revoking a membership invalidates that member's active access immediately. Schema upgrades use `PRAGMA user_version` within a transaction, and foreign keys are enabled on every connection.

The authentication sequence is `password verification → issue random session and CSRF secrets → set HttpOnly SameSite cookie → resolve digest on each request → check current membership → validate Origin and CSRF on mutation`. Passwords use scrypt with a per-user random salt and constant-time comparison. The operator bootstrap command takes its password from a TTY prompt or stdin without printing it.

Users log in with a password verified using a memory-hard hash. An operator bootstrap command creates the first admin; there is no open public registration. Browser sessions use an HttpOnly, SameSite cookie and a hashed, revocable token in SQLite. Mutating requests require a same-origin check and CSRF token. Tenant and Customer IDs from clients are always checked against current membership and parent ownership.

Membership roles are `admin` and `member`. An admin manages tenant members and the tenant model credential. Members create Customers in their tenant and can access that tenant's Customers. A Customer stores a name and type at creation; both remain editable through the admin surface only.

An admin provisions a user and membership atomically through the gateway, using a server-hashed password. Duplicate email is a conflict; there is no implicit account takeover or password reset. Admins can remove tenant memberships, which immediately clears their active Customer binding.

## Model provider distribution

The tenant admin configures exactly one custom model provider credential (provider family `custom`) on the gateway: provider name, API type (`anthropic-messages` or `openai-chat-completions`), HTTPS public base URL, model ID and API key. `EnterpriseStore` is the sole owner of this credential (AES-256-GCM at rest, tenant-bound AAD, rotation and revocation).

When a Customer runtime is prepared, the control plane **distributes** the provider into that Customer's native provider configuration (`.zcode/v2/provider_config.json`): the runtime receives the real upstream base URL and the real API key in a managed `enterprise-custom` provider slot, pinned as the default model selection. Members never configure providers: the native settings surface hides the model provider section, and the runtime server (started with `ZCODE_ENTERPRISE_MANAGED_MODEL=1`) rejects provider configuration writes, Z.ai OAuth mutations and generic credential RPCs (`enterprise.model_configuration_managed`); provider status/model reads stay available. Model traffic flows directly from the Customer runtime to the upstream provider using ZCode's native provider stack — there is no model relay on the request path, so ordinary developer environments (transparent proxies, fake-IP DNS) behave exactly like native ZCode.

Distribution invariants: the credential is written only into that Customer's runtime data volume (one Customer = one isolated container), the provision step rewrites the managed slot atomically on every runtime start, any previously managed slot (`enterprise-custom` and the removed fixed families) is replaced rather than accumulated, and unmanaged provider entries the runtime may hold are preserved. The API key never appears in gateway logs, API responses or browser state; only status projections (configured/revoked, last four) leave the store.

## Runtime and routing

```text
browser request /ws or /api/*
  → gateway authenticates user and active Customer
  → checks current membership and Customer ownership
  → runtime manager ensures the Customer runtime exists
  → gateway forwards to that runtime with its private token
  → native ZCode HTTP/RPC service executes
```

The active Customer is a server-side session property. Switching it revokes the prior browser WebSocket by closing the connection before runtime work and again after the new binding commits, then reloads the native Root so in-memory workspace/session stores cannot cross Customers. Runtime mappings survive process restarts. A startup health check reattaches or restarts a stale runtime. Removing a membership makes the next request fail; existing sockets are closed on the next authorization check or explicit membership change.

The gateway owns only in-memory live process/socket handles; SQLite owns the active Customer binding and native session ID. For every request it resolves the session, then asks SQLite for the active Customer using current membership. Activation closes this session's prior sockets before changing the binding; explicit membership removal clears the affected active Customer bindings and immediately closes all live sockets for that user. A runtime restart retains the Customer workspace and changes its private token; requests never reuse an unhealthy handle. The browser contract includes bootstrap, login/logout, tenant and Customer lists and creation, Customer activation, native session binding for the active Customer, publishing a workspace Skill, admin MCP binding endpoints and the tenant model credential endpoints under `/api/enterprise`. Mutations require CSRF and same-origin validation. Missing authentication yields 401, inaccessible Customer or parent yields 404, invalid input yields 400, and runtime unavailability yields 503. A published Skill path must resolve inside that Customer's native skills directory, including symlink resolution; the server reads and hashes its SKILL.md. An MCP secret reference names a server environment variable, resolved only while materializing an authorized Customer and never returned to browsers.

The native proxy canonicalizes and rejects malformed or multiply encoded paths before routing, denies privileged native routes, removes hop-by-hop and connection-nominated request headers, replaces browser cookies and authorization with the private runtime credential, and never forwards native cookies to the browser. Redirects must stay inside the gateway's allowed native path space. WebSocket handshakes forward only the required public upgrade headers.

The runtime manager stops an unhealthy or replaced Customer runtime before it materializes `AGENTS.md`, Skills, MCP config or the distributed model provider, then starts the replacement. Before first materialization it removes any stale named container left by an earlier gateway process. Ordinary requests reuse a healthy runtime without rewriting its writable workspace. Skill, MCP binding and model credential changes stop affected Customer runtimes before their next materialization; membership removal also revokes those runtimes' relay credentials before they are restarted by a remaining member. Gateway shutdown rejects new runtime ensures, waits for pending starts to settle, then stops every resulting live runtime before closing its listener.

Production isolation uses one unprivileged container per Customer with only that Customer's workspace/data volumes mounted; no host home, Docker socket or other tenant volume is mounted. The process adapter is development-only and makes no host-file/shell isolation claim. Runtime listeners bind loopback or a private container network and use a random per-runtime token. The gateway never returns direct runtime addresses or tokens to browsers. Native `/api/rpc-host-capability`, `/ws/host`, remote-connect and bot callback routes are denied at the gateway.

## Customer workspace, Skills and MCP

On Customer runtime preparation, the control plane writes a minimal `AGENTS.md` into that Customer's workspace. User edits to generated files are overwritten on runtime preparation; this is stated in the UI.

Publishing a native `SKILL.md` stores a tenant-scoped copy with its source Customer and content hash. Runtime preparation materializes only authorized tenant or Customer shared Skills under that Customer's `.zcode/skills`; native Skill discovery and execution stay unchanged. Runtime-specific HOME/data directories prevent a user's global Skills from leaking between tenants. MCP bindings contain a per-tenant endpoint and server-side secret reference. A secret reference must use `ZCODE_ENTERPRISE_MCP_SECRET_<TENANT_UUID_WITHOUT_HYPHENS_UPPERCASE>_<NAME>`; creation, preparation and relay each verify that its tenant prefix matches the binding tenant. Runtime preparation provides only bindings authorized for that Customer. `.zcode/config.json` contains only a gateway MCP relay URL and a random per-Customer/per-binding relay token; the upstream bearer secret stays in the gateway environment and is injected only when proxying a request. Each relay request checks the token against that exact Customer and binding, confirms the binding is still authorized for the Customer, and streams HTTP request/response bodies to the configured HTTPS endpoint. Upstream destinations are denied by default and must match the tenant entry in operator-owned `ZCODE_ENTERPRISE_MCP_ALLOWLIST_JSON`, a JSON object mapping tenant UUIDs to arrays of exact HTTPS origins or exact endpoint URLs. IP literals, localhost, userinfo, fragments, redirects and DNS answers outside public unicast space are rejected; every request pins a freshly resolved public IP for its connection. Relay concurrency is capped and a connection/header timeout applies before upstream headers arrive, while an established SSE body can remain open and propagates downstream backpressure. Stopping the runtime revokes its relay tokens. A missing secret reference emits an operator diagnostic and skips that binding without preventing ordinary Agent usage.

## Web experience

The Web entry checks whether the enterprise gateway is enabled. It shows login, a tenant switcher, and the Customer workspace list. Opening a Customer goes straight into the native ZCode workspace; a Customer can own multiple native sessions, all managed by the native UI. An always-visible Customer header wraps the existing `Root`. It passes the authorized Customer workspace path and mapped native session ID into `Root`, with arbitrary workspace opening disabled. It does not modify the Composer or mode controls. Customer switching tears down the old `Root` and WebSocket before loading the new Customer.

The Web entry probes `/api/enterprise/bootstrap` before opening a native socket. A `404` means ordinary ZCode Web mode; any other probe failure is visible and retryable. The enterprise shell owns only the current UI selection and the browser socket. The gateway owns login, membership, the active Customer, CSRF token and all business records. Login and every mutation send the bootstrap CSRF token and same-origin cookies. A Customer requires a name and type. A successful Customer activation first unmounts native Root and closes its socket, then loads the authorized bootstrap and creates a new socket/Root with the Customer path and session ID. A failed activation stays outside Root until bootstrap determines the authorized active Customer. Enterprise mode cannot open arbitrary workspaces. The shell uses Chinese/English labels based on browser language, semantic tokens, and keeps selectors and actions usable on narrow Web viewports.

All native sessions ("cases" in product language) are created, listed and resumed by the native ZCode UI inside the customer workspace; the enterprise gateway stores no native session IDs and adds no session-binding route. Session/task continuity comes from the customer runtime's own task index, so reopening a customer workspace restores its native sessions without enterprise-side state.

In the workspace ("项目") sidebar view, enterprise mode shows Customer rows only: the active Customer reuses the native workspace row with its nested task list, and new tasks are created from that workspace (sidebar new-task action, workspace row, or chat empty state). The native sidebar's standalone "任务" section (the conversation-workspace purpose section) stays hidden in enterprise mode: a customer runtime has exactly one workspace, and the conversation entry would create a second app-managed workspace inside the container, outside the Customer workspace.

## Acceptance and regression

Tests cover two tenants, multiple users/Customers, cross-tenant API and runtime denial, stale runtime mapping and stale-container removal before workspace writes, shutdown during a pending runtime start, Customer switching with late WebSocket closure, immediate membership revocation, Skill and MCP distribution, tenant-scoped secret exclusion, cross-tenant secret-reference rejection, denied non-allowlisted/private destinations, DNS pinning, fixed-binding streaming relay, backpressure, workspace isolation, container workspace mounts, and model provider distribution (real upstream base URL and key written to the managed slot, no relay URL or token, managed-slot replacement, revocation clearing the distributed provider). Container mode requires a relay origin that Customer containers can reach; production uses the configured HTTPS enterprise origin, and local Docker development uses a host interface reachable at `host.docker.internal`. Native Agent smoke tests cover session creation/continuation, Composer modes, files, shell, Skills, MCP, and streaming. The MVP is complete only when the full isolation and regression suite passes in a documented container-enabled environment.

## Migration and non-goals

Enterprise mode is opt-in and leaves the ordinary ZCode server/Desktop paths intact. SQLite schema migrations are versioned and transactionally applied; schema v4 drops the removed ServiceSpace/ServiceObject/Case tables and columns destructively — initial development stage, no backward data compatibility. No SSO, billing, workflow engine, new RAG stack, new Agent/Session runtime, or Composer rewrite is included.
