# Enterprise gateway

This opt-in gateway serves the built Web client and gives each authenticated expert one long-lived private native ZCode runtime per (user, tenant). Every Customer of that tenant is a native workspace mounted into the expert's runtime; switching Customers is a native workspace tab switch with no runtime handoff, and every native ZCode session is a case in the product language. The old per-Case hierarchy (ServiceSpace/ServiceObject/Case) is removed without a compatibility path: schema v4 drops it destructively. The gateway does not change ordinary desktop or Web entry points.

From the repository root, use Node 24 and build the native server and Web client:

```sh
pnpm install --frozen-lockfile
pnpm --filter @zcode/server build
pnpm --filter @zcode/web build
docker build -f packages/enterprise/Dockerfile.runtime -t zcode-enterprise-runtime:local .
pnpm --filter @zcode/enterprise test
RUN_ENTERPRISE_DOCKER_E2E=1 pnpm --filter @zcode/enterprise test:e2e
pnpm --filter @zcode/enterprise bootstrap-admin
pnpm exec tsx packages/enterprise/src/entry.ts
```

Set `ZCODE_ENTERPRISE_DATA_ROOT`, `ZCODE_ENTERPRISE_DB_PATH`, `ZCODE_ENTERPRISE_WORKSPACE_ROOT`, `ZCODE_ENTERPRISE_STATIC_ROOT`, `ZCODE_ENTERPRISE_PORT`, and `ZCODE_ENTERPRISE_ORIGIN` as needed. The workspace root contains Customer workspaces; the data root additionally holds one expert runtime data volume per (user, tenant). The gateway binds `127.0.0.1:3031` by default. Container mode requires `ZCODE_ENTERPRISE_RELAY_ORIGIN` or `ZCODE_ENTERPRISE_ORIGIN` to name an HTTP(S) origin reachable from expert runtimes for the MCP relay; loopback origins are rejected at startup. For production, use the same public HTTPS origin served by the TLS reverse proxy, which can continue forwarding to the loopback gateway. For local Docker testing without a reverse proxy, use `ZCODE_ENTERPRISE_RELAY_ORIGIN=http://host.docker.internal:3031` and bind the gateway to a host interface reachable by Docker with `ZCODE_ENTERPRISE_HOST=0.0.0.0`; restrict that listener with the host firewall. The container maps `host.docker.internal` on Linux and uses Docker Desktop's host mapping on macOS. The MCP relay accepts only random per-Customer, per-binding tokens and per-tenant connector tokens, and forwards to the stored endpoint; it is not an arbitrary URL proxy. Do not expose the native runtime ports.
Keep any custom data root and database outside the Docker build context. The default `.enterprise-data` is excluded by `.dockerignore`.

The default `container` adapter launches one unprivileged Docker container per expert runtime (`e-<userId>-<tenantId>`): the expert's data volume is the runtime HOME and every tenant Customer workspace is mounted into it, so all of that expert's sessions across Customers share one runtime, task index, distributed providers and HOME Skills while each Customer keeps its own workspace files. The runtime image builds the native ZCode server and CLI agent. Container port 3030 is published to a random loopback port. `ZCODE_ENTERPRISE_RUNTIME_IMAGE` chooses the image. On macOS, allow Docker Desktop access to the Customer workspace root. `ZCODE_ENTERPRISE_RUNTIME_MODE=process` is available for local development only; it does not isolate host files or shell operations.

Two optional capacity settings bound how many expert runtimes stay warm; both default to off so development behavior is unchanged. `ZCODE_ENTERPRISE_RUNTIME_IDLE_MINUTES` (integer ≥ 1) enables an idle reaper: an expert runtime with no attached session socket for the whole window is stopped through the same fail-fast path used by tenant mutations (attached sockets are destroyed first, and the browser shell self-heals by reconnecting, which re-prepares the runtime on demand). MCP relay traffic is not counted as activity — relay requests originate from the runtime's own container, so a reaped runtime cannot produce them and an open browser tab (whose socket keeps the runtime active) is the only client worth keeping warm. `ZCODE_ENTERPRISE_MAX_RUNTIMES` (integer ≥ 1) caps concurrently running runtimes: when admitting a new expert runtime would exceed the cap, the least-recently-active live runtime is evicted first (preferring runtimes with no attached sockets; the evicted expert's sockets are destroyed fail-fast and self-heal). If nothing is evictable, the gateway admits anyway and emits a `ZCODE_ENTERPRISE_RUNTIME_CAP_EXCEEDED` warning rather than blocking login; under sustained overload this can thrash, which is accepted and visible. Both settings exist for capacity-bounded hosts (a 4-core/8-GB ECS keeps roughly 3 warm expert containers).

Each enterprise runtime adapter injects `ZCODE_ENTERPRISE_MANAGED_MODEL=1` into the native server. The native server uses that marker to keep tenant model configuration and runtime storage as the sole responsibility of the enterprise control plane: provider configuration writes, Z.ai OAuth mutations, OAuth session restoration, database-root changes, and generic credential read/write RPCs are rejected or return a signed-out result; rejected calls use `enterprise.model_configuration_managed`. Provider status/model reads and ordinary settings such as locale remain available. A normal ZCode Web, remote workspace, or Desktop continuous server started without this marker keeps its existing behavior. The adapters also inject `ZCODE_ENTERPRISE_MANAGED_CONTENT=1`, under which the native skill-management and MCP config write paths reject create/update/delete operations whose target name uses the reserved `enterprise-` prefix (`enterprise.managed_content`), so tenant-distributed skills and connector entries cannot be tampered with between preparations.

## Model provider catalog

The tenant admin maintains a provider catalog (schema v7 `tenant_model_providers`): any number of providers, each with a unique `provider_key`, API type, HTTPS base URL, API key, model list, default model and a tenant-wide default marking. When an expert runtime is prepared, the gateway writes every enabled provider into the expert's native provider configuration (`.zcode/v2/provider_config.json` inside the expert data volume) as managed `enterprise-<provider_key>` slots: the runtime receives the real upstream base URLs and API keys and connects to the providers directly through the native provider stack — there is no model relay on the request path, so ordinary developer environments (transparent proxies, fake-IP DNS) behave exactly like native ZCode. The tenant-default provider pins the default model selection; switching models among the distributed slots stays native. Members never configure providers (`ZCODE_ENTERPRISE_MANAGED_MODEL`; the settings UI hides the native provider editor). Catalog changes stop the tenant's expert runtimes so the next open re-distributes. An admin-only connection-test route performs a best-effort model list against a provider and returns `{ok, models?, error?}` without ever logging the key. Migration v7 seeds one provider row from the legacy single credential; the legacy `model-credentials` HTTP routes are gone.

Configure `ZCODE_ENTERPRISE_MCP_ALLOWLIST_JSON` before adding MCP bindings. It maps each tenant UUID to allowed HTTPS origins or exact endpoints, for example `{"tenant-uuid":["https://knowledge.example.com"]}`. Missing or malformed entries deny the binding. DNS results must all be public addresses; the relay connects to a validated address while retaining the hostname for TLS. `secretRef` must name an environment variable with the tenant's compact uppercase UUID: `ZCODE_ENTERPRISE_MCP_SECRET_<TENANT_UUID_WITHOUT_HYPHENS>_<NAME>`. The gateway resolves it in the gateway process and injects it only when relaying requests to the stored upstream endpoint. A Customer workspace receives a scoped, revocable relay token and URL; it never receives the upstream secret. If a reference is missing, that binding is skipped and reported as a gateway warning. Keep the workspace root and gateway data readable only by trusted operators.

## User management

Users are global identities; membership administration is tenant-scoped and admin-only. The routes (all under `/api/enterprise/tenants/:tenantId`, all mutations CSRF-checked) replace the old bare `POST /api/enterprise/users` and member-delete routes: `GET .../users` lists members (email, display name, role, status, Customer-access summary); `POST .../users` creates by email — a brand-new email creates a global user with an initial password plus the membership (`joined:false`), while an email that already exists globally is simply joined into the tenant without a password (`joined:true`, the identity keeps its own credentials); an email that is already a member of this tenant returns 409. `PATCH .../users/:userId` edits display name, role and password (admin reset), and disables (`status:"disabled"`) or re-enables the account; `DELETE .../users/:userId` removes the membership only — the global user row survives because it may belong to other tenants.

Guards (both return 409): an admin cannot demote or disable **themselves**, and the tenant's **last active admin** cannot be demoted, disabled or removed — preventing lock-out. Disabling is a global kill switch for that identity: login is rejected on the same invalid-credentials path (which check failed is not revealed), session validation rejects the user immediately (`users.status` is enforced on every `resolveSession`, so existing sessions die even before their socket sweep), the user's sockets are destroyed and their expert runtimes in that tenant are stopped. A role or status change stops **only that user's** runtimes in the tenant (mount sets are fixed at container start; browsers self-heal by reconnecting); display-name or password-only changes stop nothing. Removal likewise closes the user's sockets and stops their runtimes, and clears their Customer-access grants for the tenant.

## Customer visibility

Schema v9 adds `customer_access_grants` (allowlist semantics). A member with **no grants sees all** of the tenant's Customers (the previous trust-all default, backward compatible); once any grant exists, the member sees exactly the granted Customers. Admins are never restricted. Enforcement is total, not cosmetic: the Customer list API filters per member (`GET /api/enterprise/customers`); activating a non-visible Customer returns 404; the bootstrap's last-activated Customer resolves to `null` when no longer visible (the shell auto-activates the first visible one); the importable-skills scan only walks visible workspaces; and — the security boundary — **expert runtime mounts are filtered**: the gateway mounts only visible Customer workspaces for that member, and the primary workspace (`ZCODE_SERVER_WORKSPACE`) must itself be a visible Customer (fallback: the first visible one; none visible: the original primary with an empty mount set, self-healing once an admin grants access).

`PUT .../users/:userId/customer-access` (admin) sets the mode: `{mode:"selected", customerIds}` requires a non-empty list whose ids are all Customers of this tenant (400 otherwise) and replaces the grant set atomically; `{mode:"all"}` clears the grants. Grant or role/status changes stop the affected user's runtimes so the next open re-mounts the new set; other experts are untouched.

## Catalog storage and key custody

`EnterpriseStore` is the sole owner of provider API keys. Each catalog row stores its key in `tenant_model_providers.api_key_encrypted` as an AES-256-GCM envelope (ciphertext, nonce, auth tag) plus the last four characters, so status projections never decrypt. The encryption key is a required 32-byte constructor value. The enterprise entry resolves `ZCODE_ENTERPRISE_MODEL_CREDENTIALS_KEY` first (base64, `base64:` or `hex:` encoded), then uses a generated 0600 local `model-credentials.key` under the configured data root when no environment value is supplied. The resolved key is never persisted in SQLite, browser state or gateway logs; inside an expert runtime it exists only as the distributed provider configuration. Decryption is bound to the tenant and `provider_key` as additional authenticated data, so moving a row between tenants or keys fails closed.

The admin-only store commands are `createTenantModelProvider`, `updateTenantModelProvider` and `deleteTenantModelProvider`; they verify tenant membership and the `admin` role before writing. `listTenantModelProviders` is the browser-facing projection (enabled/default state, model list, at most the final four key characters); `tenantModelProvidersForDistribution` and `tenantModelProviderForConnectionTest` are gateway-internal decrypted reads. The migration from schema version 6 to 7 creates the catalog table transactionally and seeds it from the legacy single credential; a missing or wrong encryption key fails the migration loudly rather than dropping a tenant's model access. API keys are never included in errors or logs.

## Tenant connectors and Skill promotion

Tenant connectors (`tenant_mcp_connectors`, schema v7) are the admin-managed MCP layer distributed into every expert runtime's HOME `.zcode/config.json` as `enterprise-<connector_key>` entries pointing at the gateway relay (`/api/enterprise/mcp-relay/t/<connectorId>`) with a stable per-connector token; the expert's personal MCP entries survive the managed merge. Connector endpoints and secret references follow the same allowlist and `ZCODE_ENTERPRISE_MCP_SECRET_<TENANT_UUID_WITHOUT_HYPHENS_UPPERCASE>_<NAME>` rules as Customer bindings, and the relay path is identical (token check, DNS pinning, concurrency caps). Connector mutations stop the tenant's expert runtimes.

Admins promote existing Skills into the tenant layer: `GET /api/enterprise/tenants/:tenantId/importable-skills` lists importable Skills from the acting admin's expert HOME and every Customer workspace (the four native discovery roots, managed `enterprise-*` excluded) with descriptions, origins and already-imported markers; `POST /api/enterprise/tenants/:tenantId/skills/import` takes name + origin (+ workspace) — native skill-creator writes new Skills to the project level by default, so imports must cover workspaces, not only HOME. Both stop tenant expert runtimes for redistribution. In addition, expert runtime preparation seeds the bundled baseline Skill set (`skill-creator`, vendored under `runtime-seed/skills/`) into the expert HOME `~/.agents/skills/` — if-missing only, never overwriting personal content — because the container has no plugin store and managed mode rejects Z.ai OAuth, so plugin-provided skills would otherwise be absent.

## Baseline plugin seeding

Set `ZCODE_ENTERPRISE_PLUGIN_SEED_ROOT` to an operator-owned host directory of curated official plugins. The layout is `<name>/<version>/`, mirroring what a working desktop keeps under `~/.zcode/cli/plugins/cache/zcode-plugins-official/` — the practical way to curate it is to install the plugins on a working desktop and copy the cache directories you want. A relative path resolves against the gateway working directory. Leave the variable unset to disable plugin seeding entirely.

At expert runtime preparation each plugin is copied if-missing into the expert HOME `~/.zcode/cli/plugins/cache/zcode-plugins-official/<name>/<version>/`, and `~/.zcode/cli/config.json` is merged — never rewritten — to set `plugins.enabledPlugins["<name>@zcode-plugins-official"] = true` for each curated plugin, because plugins outside the compile-time default-enabled set need this entry to load. The agent's official-cache scan is restricted by a whitelist it rewrites from image assets on every startup, so preparation also merges the install registry `~/.zcode/cli/plugins/installed_plugins.json` (records with `installPath: ""`, which resolves to the seeded cache directory) — discovery loads the registry without any whitelist, and it is what makes seeded plugins actually load. Both merges preserve every other key of the file (they also hold native CLI state), write atomically (staging + rename), and only write when the merged content actually differs from what is on disk; a file that cannot be safely parsed or merged (invalid JSON, unexpected shapes) is left byte-identical with a `ZCODE_ENTERPRISE_PLUGIN_CONFIG_INVALID` / `ZCODE_ENTERPRISE_PLUGIN_INSTALL_INVALID` warning instead of being destroyed.

Seeded directories carry the same `.enterprise-seed.json` digest marker as seeded skills: when the seed root advances, pristine copies are refreshed (staging copy + single rename) and expert-modified copies are never touched. Seeding never removes plugins — dropping one from the seed root leaves the existing copy in the HOME cache, and removal is a HOME-level operation. An expert disabling a seeded plugin is re-enabled by design on the next runtime restart: every preparation re-asserts the enabled entries, because the baseline set is managed.

This path exists because the container agent never obtains plugin content by itself (managed mode rejects Z.ai OAuth), while a pre-seeded cache directory loads fully offline at session start — skill and command scans are local disk reads. Curate for command and plugin-MCP value that the bundled skill seeding does not already cover: `superpowers` is the canonical pick. Avoid duplicating the bundled skill set — `zcode-guide`, `skill-creator` and the document skills (`docx`, `pdf`, `pptx`, `xlsx`) are already seeded as plain skills, and adding their plugin forms too makes every skill appear twice in the catalog (usable but noisy). GUI or hardware-dependent plugins are useless in a server container; the `zcode_official`-auth plugin MCP fails by design in managed mode. No marketplace metadata is seeded — loading needs only the cache content, the enabled entry and the install registry — and the store UI stays unusable-but-harmless offline.
